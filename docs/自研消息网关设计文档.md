# 蜂鸟（Hummingbird）· 自研消息网关设计文档

> 版本 v0.8 · 2026-11-09 · 目标设备：树莓派 3B+（1GB RAM，arm64/armv7）
> 定位：自托管多渠道消息推送网关，单二进制 + SQLite，极致省内存。
> v0.2 修订：去除 async 运行时（tokio/axum/reqwest → 同步栈），空闲 RSS 目标 <15MB → <8MB。
> v0.3 修订（需求方确认砍项）：内置定时消息 → 系统 cron 替代；多用户 → 单用户（schema 保留 user_id）；登录日志表 → 进程日志；站点样式配置 → P3。
> v0.4 修订（需求方确认）：取消里程碑分期，全部范围一次交付；email 渠道、导出报表移出范围（非原始需求）。
> v0.5 修订（需求方要求）：交付物收敛为单文件——musl 静态二进制内嵌前端资源与 systemd unit，`hummingbird install` 一条命令成服务。
> v0.6 修订（需求方要求）：去掉自安装——只交付一个可执行二进制（前端内嵌，无独立前端程序），无参数即前台运行；服务化/自启动由用户自行配置（附 unit 模板文档《自研消息网关运行时默认与自启动.md》）。
> v0.7 修订（需求方确认）：push API 支持批量——一次调用多条消息，各自模板/变量/渠道（顶层默认 + 单条覆盖）；push_logs 增 batch_id；渠道限速错误如实返回，不内置重试。
> v0.8 修订（需求方要求）：引入**任务（Task）**模型——token 与任务 1:1 绑定，任务绑定多个模板，每模板对应一组渠道，调用时只传模板+变量，渠道由绑定决定（取代 v0.7 调用时指定渠道）；独立 api_tokens 表取消。任务 ≠ 定时器，触发仍由外部发起。

## 1. 目标与非目标

**硬性目标**

| 指标 | 目标值 |
|---|---|
| 空闲 RSS | **< 8 MB**（同步栈基线约 3–6MB，留余量；登录瞬时 argon2 峰值另计） |
| 二进制体积（musl 静态） | < 10 MB（含内嵌前端） |
| 冷启动 | < 1 s |
| 7×24 稳定性 | 内存曲线平稳，无泄漏增长 |
| 部署形态 | 单个可执行二进制（前端内嵌，无独立前端程序），无参数即前台运行；服务化由用户自行配置 |

**功能目标**（单阶段一次交付）：Web 管理台、登录（单用户，schema 预留 user_id）、SQLite、8 渠道推送（含渠道级代理）、消息模板（关键词替换）、推送日志（自动清理）、外部通用 API（自生成 token）、站点样式配置（标题/标语/图标/主题色）。

**非目标（明确裁剪）**

- ❌ 单点登录（SSO）：无身份源（Authentik 等）、无第二个消费方，确认无收益，裁剪（2026-11-09 需求方确认）。
- ❌ 微信公众号/测试号直发：合规通道收紧风险，微信触达统一走企微应用消息（可直达个人微信）。
- ❌ 双向聊天/收消息：只做出站推送。
- ❌ 内置定时消息：与系统 cron/systemd timer 职责重复，定时需求由系统调度 curl push API 承担（见 §7）。
- ❌ 登录日志入库：单用户无取证对象，登录事件写进程日志（journalctl 可查）；防爆破锁定保留。
- ❌ 集群/水平扩展：单实例是特性，不是缺陷。
- ❌ email 渠道、导出报表：非原始需求（设计者添加的"按需"项），2026-11-09 确认移出。

## 2. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | Rust (edition 2021+) | 空闲内存最优、无 GC 抖动、auth/SQL 代码安全 |
| 并发模型 | **同步阻塞 + std 线程**（无 async runtime） | 本应用并发 = 管理台偶发请求 + 每条推送一个线程，同步模型天然匹配；砍掉 tokio 4 个 worker 线程栈与调度器 |
| Web 框架 | **tiny_http** + 手写路由（~20 行；嫌素可加 rouille） | axum→tiny_http 省 hyper/tower 全家；路由总共 ~15 条 |
| SQLite | rusqlite（bundled feature），**单连接 + Mutex** | 编译内置 SQLite；WAL 模式；`cache_size=-512`、`mmap_size=64MB` |
| HTTP 客户端 | **ureq**（rustls，socks-proxy feature） | 同步、极小；socks feature 正好接本机 mihomo 给 Telegram 出站 |
| 密码哈希 | argon2 crate，**参数调优 m=8MiB/t=2/p=1**（内网强度足够） | 默认参数 m=19MiB 每次登录瞬时吃 20MB+ 堆，必须调低；登录瞬时峰值在内存预算中已注明 |
| 模板引擎 | **自实现 `{{var}}` 替换（约 30 行）** | tera/handlebars 为此场景过重；零依赖极致路线 |
| 前端 | Vue 3 + Vite，构建产物 rust-embed 内嵌 | 前端只影响客户端，不影响服务内存 |
| 构建 profile | `opt-level="z"` + `lto="fat"` + `codegen-units=1` + `strip` + `panic="abort"` | 二进制 −30~50%，映射代码页减少带动 RSS 下降 |
| 交叉编译 | cargo-zigbuild → aarch64/armv7 musl | 完全静态二进制，Pi 上零依赖直接跑 |

**明确不引入**（防倒退）：jemalloc / mimalloc（小应用反而增肥）、tokio/async 全家（本项目无收益）、tera/handlebars、任何 ORM。

## 3. 内存预算与措施

```
二进制映射（含 embed 前端）  ~5 MB（opt-level=z + lto 后，按需换入）
SQLite 单连接（cache 512KB） ~1 MB
ureq 连接（按渠道惰性建）    ~0.5–2 MB（峰值）
4 个 std 线程栈（实际触页）  ~0.5 MB
─────────────────────────────
空闲 RSS 目标                 3–6 MB（验收线 < 8 MB）
推送+Web台并发峰值           < 16 MB
登录瞬时（argon2 m=8MiB）    +9 MB（转瞬即逝，MemoryMax 内）
systemd 兜底                 MemoryMax=64M
```

关键纪律：

1. SQLite **单连接 + Mutex**，`busy_timeout=5s`，WAL 模式，`cache_size=-512`，`mmap_size=64MB`（页走可回收 page cache，不占堆）。
2. 推送日志批量落库（攒 1s 或 20 条 flush），避免高频写。
3. 推送日志自动清理：后台任务每日删 `push_logs` 超期行（默认保留 90 天，可配）。
4. ureq Agent 全局单例，每渠道 host 连接复用 keep-alive。
5. 无常驻大 buffer：消息体上限 64KB，超限拒绝。
6. 线程模型：主线程 = HTTP accept；每连接短命线程（tiny_http 自带）；日志清理等后台任务临时 spawn 完成即回收。无常驻后台线程。

## 4. 数据模型（SQLite）

```sql
users        (id, username UNIQUE, password_hash, role[admin|user],
              created_at, last_login_at)

sessions     (token_hash PK, user_id, expires_at, ip, user_agent)

channels     (id, user_id, type, name, config_json, enabled,
              created_at)
              -- type: dingtalk_bot | wecom_bot | wecom_app | feishu_bot
              --       | telegram | bark | ntfy | webhook（8 种）
              -- config_json 通用字段: proxy(null=直连 | "http://…" | "socks5://…")、
              --                      timeout_ms(默认 10000) + 各渠道私有字段

templates    (id, user_id, name, title_tpl, body_tpl,
              variables_json, created_at)                -- variables: [{key, desc, default}]

tasks        (id, user_id, name, enabled,
              token_hash, token_prefix, token_last_used_at,
              created_at, updated_at)
              -- 任务 = 推送授权+路由单元（≠定时器，触发由外部 cron/脚本发起）
              -- token 与任务 1:1（内嵌列，无独立 tokens 表）
              -- 明文 token 仅创建/重生成时展示一次；重生成后旧 token 立即失效

task_bindings (id, task_id, template_id, channel_ids_json)
              -- 一行 = 一个"模板 → 渠道组"绑定；任务可绑多个模板；
              -- 同一任务内模板唯一 UNIQUE(task_id, template_id)——
              -- 要不同渠道组合就另建任务，不做歧义路由

push_logs    (id, user_id, task_id, template_id, batch_id, channel_id,
              title, content_brief, status[ok|failed], via_proxy, error,
              cost_ms, created_at)
              -- task_id/template_id: 溯源"哪个任务的哪个模板发出的"
              -- batch_id: 同一次批量调用的分组键（单发时与 id 同值）
              -- via_proxy: 该条是否经代理出站（排 Telegram 问题用）
              -- 索引 (user_id, created_at DESC)

settings     (key PK, value)   -- site_title | site_slogan | site_icon(b64)
                                   | theme_color | log_retention_days
```

**单用户设计**：`users` 表常态仅一行（admin），无用户管理界面。业务表保留 `user_id` 列（schema 向前兼容，未来多方需求无痛升级），代码经 repository 层统一注入。首次启动自动建 `admin` 账号（随机密码打印到 stdout，首次登录强制改密）。

## 5. API 设计

浏览器走 session cookie（HttpOnly + SameSite=Strict）；外部调用走**任务 token**：`Authorization: Bearer <task_token>`。token 能发什么模板、发到哪些渠道，完全由该任务的绑定决定，调用方不可指定渠道。

```
认证    POST /api/auth/login | POST /api/auth/logout | GET /api/auth/me
渠道    GET/POST /api/channels | PUT/DELETE /api/channels/:id
        POST /api/channels/:id/test          -- 发测试消息（排障神器，兼代理验证）
模板    GET/POST /api/templates | PUT/DELETE /api/templates/:id
        POST /api/templates/:id/render       -- 传 variables 预览替换结果
任务    GET/POST /api/tasks | PUT/DELETE /api/tasks/:id   -- CRUD；更新含改绑定
        POST /api/tasks/:id/token/regenerate -- 重生成 token（旧 token 立即失效）
        POST /api/tasks/:id/test             -- 按绑定逐模板逐渠道发测试
日志    GET /api/messages?task=&status=&channel=&page=   -- 推送日志（可按任务过滤）
设置    GET/PUT /api/settings                -- 站点标题/标语/图标/主题色/日志保留天数

── 外部推送接口（任务 token 认证；渠道由绑定决定）──
POST /api/push     单发：{ "template": "巡检",              -- 模板名或 id，须绑定于该任务；
                                                          -- 任务仅一个绑定时可省略
                     "variables": {"host": "pi"} }          -- 渲染后发往该绑定的全部渠道
     批量：{ "messages": [ {"template": "巡检", "variables": {"host": "pi"}},
                          {"template": "备份", "variables": {"size": "2G"}} ] }
     约束：单次 ≤ 20 条、单条 ≤ 64KB；响应 results[] 按 消息×渠道 逐条返回
     （msg 序号 + template + status/error/via_proxy/cost_ms）；
     渠道官方限速（钉钉/企微 ≈20 条/分）错误如实返回，不内置重试。
GET  /push/:token?template=巡检&host=pi   -- 一行流：template 之外的任意查询参数即变量
```

校验失败 fail-fast 返回 4xx + 明确错误码；推送部分失败返回 207 语义（逐渠道结果数组）。token 引用未绑定的模板 → 403。

## 6. 渠道抽象

```rust
pub trait Sender: Send + Sync {
    fn send(&self, msg: &OutMessage) -> Result<ChannelReceipt>;   // 同步，ureq 出站
}
```

每渠道一个 impl + serde 反序列化的 config struct。全部为出站 HTTP：

| 渠道 | 实现 | 备注 |
|---|---|---|
| dingtalk_bot | POST webhook（HMAC-SHA256 加签） | ~40 行 |
| wecom_bot | POST webhook（可选 key 拼接） | ~30 行 |
| wecom_app | access_token 获取+缓存+过期刷新，发应用消息 | 唯一有状态渠道，~120 行 |
| feishu_bot | POST webhook（可选签名） | ~40 行 |
| telegram | Bot API sendMessage | proxy 字段填本机 mihomo 出站 |
| bark / ntfy | HTTP GET/POST | ~20 行 |
| webhook | 通用 POST JSON | 兜底万能渠道 |

**渠道级代理（通用能力，不只 Telegram）**

- 每个渠道 `config_json.proxy`：`null`（默认直连，钉钉/企微等国内渠道）或 `http://127.0.0.1:7890` / `socks5://127.0.0.1:7891`（指向本机 mihomo）。mihomo 自身的分流规则决定流量最终走向——网关只负责"要不要进代理"。
- 进程内按 proxy URL 缓存 ureq Agent（常态仅 2 个：直连 + mihomo），keep-alive 复用，不为每条推送重建连接。
- 出站统一 10s 超时（`timeout_ms` 可按渠道覆盖）；代理不可达 → 推送失败，错误明确写入 push_logs。
- `GET /api/channels` 返回时对 config 中 secret 类字段（webhook 签名/token/代理凭证）打码。

## 7. 定时触发（外部化，不内置）

不做内置调度器（2026-11-09 确认裁剪）：与系统 cron/systemd timer 职责重复。定时需求一行搞定：

```bash
# 系统 cron / systemd timer 调 push API，模板+变量全支持
*/5 * * * * curl -s -H "Authorization: Bearer <token>" \
  http://127.0.0.1:8080/api/push \
  -d '{"template":"巡检","variables":{"host":"pi"}}'
```

收益：少一个常驻线程、一张表、一套错过补发逻辑，管理台少一整块 UI。

## 8. 安全设计

- argon2id 密码哈希；登录失败 5 次锁 15 分钟（per username + per IP 双维度）。
- 任务 token：只存 SHA-256（tasks 表内嵌列），明文仅创建/重生成时展示一次，`token_prefix` 存前 8 位识别。**最小权限**：token 只能发其绑定模板、只发往绑定渠道，泄露影响面 = 单个任务，可即时重生成。
- session 固定 7 天过期，登出即删。
- 登录事件（成功/失败/IP/UA）写进程日志（stdout → `journalctl -u hummingbird`），不入库。
- SQL 全参数化（rusqlite 天然）；无字符串拼 SQL。
- 服务本身只听 HTTP：TLS 交给前置 `tailscale serve` / 反代（呼应旁路架构，不在小内存进程里背 TLS）。
- CSRF：SameSite=Strict cookie + 非 GET 请求校验 `X-Requested-With` 头。

## 9. 前端（Web 管理台）

- Vue 3 + Vite 单页应用，路由：登录 / 概览（今日推送统计）/ 渠道 / 模板 / **任务（绑定管理 + token 展示/重生成）** / 日志 / 设置。
- 站点配置（标题/标语/图标/主题色）由 `GET /api/settings` 启动时拉取，CSS 变量注入主题色。
- 构建产物 `rust-embed` 进二进制，部署零文件。

## 10. 交付形态：单个可执行文件

交付物 = **一个 musl 静态二进制 `hummingbird`**（arm64 / armv7 各构建一份），前端静态资源内嵌，**无独立前端程序**；启动与服务化完全由用户自行配置，二进制不做任何系统改动。

CLI（仅一个附加子命令）：
- `hummingbird`（无参数）：前台启动服务
- `hummingbird reset-password`：重置 admin 密码，新随机密码打印 stdout（密码存于 .db，必须提供重置途径）

运行时默认值（完整说明见《自研消息网关运行时默认与自启动.md》）：

| 项 | 默认 | 覆盖方式 |
|---|---|---|
| 数据库 | `./hummingbird.db`（相对工作目录，首次启动自动建） | 环境变量 `HB_DB_PATH` |
| 日志 | stdout/stderr（前台=终端；systemd 下进 journal） | — |
| 监听 | `0.0.0.0:8080` | 环境变量 `HB_PORT` |

```
hummingbird/
├── crates/server/          # tiny_http + 全部后端
│   └── src/                # main(路由)/api_auth/api_admin/auth/channels/config/db/http/push/tmpl
│                           # SQLite DDL 在 db.rs 内，启动时自动执行
└── web/                    # Vue3 前端（独立 npm 工程，构建产物 embed 进二进制，不随交付物分发）
```

## 11. 交付范围（单阶段，无分期）

功能已精简，取消里程碑分期，一次交付：

- 后端：登录（单用户）+ **任务（token 与模板/渠道绑定，取代独立 token）** + SQLite（单连接 WAL）+ 推送日志与自动清理 + `{{var}}` 模板引擎 + 8 渠道（dingtalk_bot / wecom_bot / wecom_app / feishu_bot / telegram / bark / ntfy / webhook，全部支持渠道级代理）
- API：管理 API（session）+ 外部推送 API（任务 token，单发/批量/GET 一行流，渠道由绑定解析）
- 前端：Vue3 管理台（登录/概览/渠道/模板/任务/日志/设置[含站点样式配置]）
- 交付物：单个可执行二进制 `hummingbird`（前端内嵌）+ 配套文档（部署指南、运行时默认与自启动）

开发顺序内部仍建议按依赖走（auth → 渠道 → 模板 → 前端），但不存在阶段验收门槛。
