# 蜂鸟（Hummingbird）· 推送失败自动重试提案

> 状态：**已评审定稿（2026-11-16，需求方逐项确认），待实现**
> 关联设计文档：《自研消息网关设计文档》§4/§5（本提案落地时同步修订为 v0.9）
> 关联讨论：探索勘察 + 7 轮 grill 评审，全部决策均有需求方确认记录（见 §2）

## 1. 背景与动机

网关的核心场景是服务器告警推送。渠道偶发抖动（网络超时、代理瞬断、上游 5xx）会导致告警丢失，
而调用方（cron / 监控脚本）通常只发一次、不会自己重试。网关作为"最后一公里"，应当承担
**瞬时失败的自愈责任**。

⚠️ 本提案**反转 v0.7/v0.8 的既有裁剪决策**（设计文档 §5："渠道官方限速错误如实返回，不内置重试"）。
反转理由：调用方重试成本高、告警场景送达率优先；限速类确定性失败重试后仍会失败并如实落日志，
不会造成虚假成功率。设计文档需随本提案修订。

## 2. 决策记录（全部经需求方确认）

| # | 决策 | 选择 | 被否决的备选 |
|---|---|---|---|
| D1 | 哪些失败重试 | **所有发送失败都重试**（网络错误、超时、业务拒绝 errcode≠0） | 仅瞬时错误（需给 Receipt 加错误类别，被否：无需区分，实现更简） |
| D2 | 执行模型 | **任务级可配**：次数（默认 3）+ 模式（同步 / 异步） | 全局单一模式 |
| D3 | 异步实现 | **落库 + 懒触发** | 常驻后台线程（违反 §3 铁律） |
| D4 | 参数位置 | **前端任务表单配置** | 固定常量；全局 settings |
| D5 | 参数边界 | `max ∈ 0..10`、`base_ms ∈ 100..60000`，越界 400 拒绝 | 无上限（同步模式可阻塞请求数十小时） |
| D6 | base_ms 暴露 | 表单"高级"折叠区，默认 1000 | 仅 API 可配 |
| D7 | drain 载体 | **临时短命线程**（AtomicBool 防重复 spawn）+ 单次上限 20 条 | 请求线程内同步 drain（管理台读请求可被背 200s） |
| D8 | 队列陈旧策略 | 禁用任务 drain 跳过；删除任务 CASCADE 清队；**滞留 >1h 判终态失败 `retry expired`** | 无限滞留（发出过时告警是噪音） |
| D9 | 异步 batch_id | 首批响应 `batch_id: null`，终态日志各自独立成批 | 等待终态回填（响应被无限期阻塞） |
| D10 | 队列可视化 | 不做队列页，仅 overview 加待重试计数 | 完整队列管理页（瞬态数据，排障价值低） |
| D11 | 默认模式 | `sync`（调用方拿到真实送达结果） | async |

**明确不重试**（发送前的确定性失败，无从重试）：模板未绑定（403）、无绑定渠道、64KB 超限、
渠道缺失/停用（`channel missing/disabled`）。`POST /api/channels/:id/test` 与
`POST /api/tasks/:id/test` 保持单发实况，不参与重试。

## 3. 配置模型

任务表新增 `retry_json` 列（沿用 `channel_ids_json` 的 `*_json` 风格）：

```json
{"enabled": true, "max": 3, "mode": "sync", "base_ms": 1000}
```

- `max`：**重试次数**（不含首发）。`max=3` = 最坏 1 首发 + 3 重试 = 4 次尝试；`max=0` 等价关闭。
- `mode`：`sync`（同步在线重试）| `async`（落库 + 懒触发）。
- 校验（fail fast，越界 400）：`max: 0..10`、`base_ms: 100..60000`、`mode ∈ {sync, async}`。
- 新建任务未指定时取上述默认值。

### 退避算法

纯函数 `backoff_ms(base_ms, retry_index) = base_ms × 2^(retry_index-1)`，retry_index 从 1 起：
第 1/2/3 次重试前分别等待 1s / 2s / 4s（base=1000 时，累计 sleep 7s）。不加 jitter
（单机单实例、渠道粒度并行，无同步风暴场景）。

## 4. 同步模式（sync）

在现有"每消息×每渠道一条短命线程并行发送"的结构内加重试循环：

```
attempt 1 → 失败 → sleep(backoff(1)) → attempt 2 → 失败 → sleep(backoff(2)) → ... → 成功或耗尽
```

- 渠道并行不变，批量总耗时 = 最慢渠道；`cost_ms` 记为全程累计耗时。
- 响应 `results[]` 每项增加 `"retries": n`（0 = 首发成功）。
- 最坏单渠道延迟 ≈ 4 次尝试 × timeout_ms(默认 10s) + 7s 退避 ≈ **47s**，README 注明调用方超时建议。
- GET `/push/:token` 一行流走同一 `do_push` 路径，自动获得重试。

## 5. 异步模式（async）

### 5.1 入队

首发尝试仍在推送请求内同步完成（async 只是把**重试**延后）。首发失败 → 写入 `retry_queue`，
响应该项 `status: "retrying"`，`batch_id: null`（D9）。

### 5.2 新表 retry_queue

```sql
CREATE TABLE IF NOT EXISTS retry_queue (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id       INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
    template_id   INTEGER,
    channel_id    INTEGER,            -- 无外键：渠道可能中途被删，drain 时判终态失败
    title         TEXT NOT NULL,      -- 存完整渲染后文本（push_logs 只有 80 字 brief，不够重发）
    body          TEXT NOT NULL,
    attempts      INTEGER NOT NULL,   -- 已尝试次数（入队时 = 1）
    max_retries   INTEGER NOT NULL,   -- 任务配置快照（任务改配置不影响已入队条目）
    base_ms       INTEGER NOT NULL,   -- 同上
    next_retry_at TEXT NOT NULL,      -- UTC，格式同 push_logs.created_at
    last_error    TEXT,
    created_at    TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_retry_queue_due ON retry_queue (next_retry_at);
```

### 5.3 懒触发 drain

触发点：`do_push` 收尾（与 `maybe_cleanup` 同模式）+ `GET /api/messages` + `GET /api/overview`
（管理台刷新即推动重试）。触发时若 AtomicBool 未置位 → 置位并 spawn **临时短命线程**执行 drain
（§3"临时 spawn 完成即回收"允许；请求零阻塞），完成后复位。

drain 单次流程（上限 20 条，按 `next_retry_at` 升序）：

1. **过期**：`created_at` 距今 > 1h → 写 push_logs（failed，`error='retry expired'`）→ 出队。
2. **任务禁用**：跳过（保留，重新启用后继续）。
3. **渠道缺失/停用**：写 push_logs（failed，`channel missing/disabled`）→ 出队（确定性失败不重试）。
4. **乐观占位领取**：锁内 `UPDATE retry_queue SET next_retry_at = <now + backoff(attempts+1)>
   WHERE id = ? AND next_retry_at = <读到的值>`，`rows_changed = 0` 视为被并发领取，跳过。
5. 锁外真实发送（重读渠道最新配置）：
   - 成功 → push_logs（ok，`retries = attempts`）→ 删除队列行；
   - 失败 → `attempts += 1`；若已达 `max_retries + 1` 次尝试 → push_logs（failed，`retries =
     max_retries`，`error = last_error`）→ 出队；否则占位时写入的 `next_retry_at` 即生效，继续等待。

### 5.4 日志语义（D9）

`push_logs` 每条消息×渠道**只在终态写一行**，带 `retries` 与最终结果——统计页不出现
"一单两行"重复计数；未决状态由 `retry_queue` 本身承载（落库，进程重启不丢）。

## 6. 数据模型与迁移

| 变更 | 方式 |
|---|---|
| `tasks.retry_json TEXT NOT NULL DEFAULT '{"enabled":true,"max":3,"mode":"sync","base_ms":1000}'` | 存量库 ALTER TABLE（pragma table_info 探测后 `ADD COLUMN`）+ SCHEMA 同步更新 |
| `push_logs.retries INTEGER NOT NULL DEFAULT 0` | 同上 |
| `retry_queue` 新表 | `CREATE TABLE IF NOT EXISTS`，无需迁移 |

内存影响：一张小表 + 两列，常态 RSS 无感知变化；**零新依赖**，二进制体积不变。

## 9. 已知副作用（文档需注明）

1. **重复消息（at-least-once）**：超时但对方实际已收到时，重试必然造成重复发送。告警场景可接受。
2. **异步滞留**：懒触发意味着重试最多等到"下一次任意推送 / 管理台读取"。低流量设备上可能滞留
   分钟~小时级（受 §5.3 的 1h 过期窗口兜底）。异步模式适合容忍延迟的场景。
3. **同步模式长尾延迟**：最坏 ~47s/渠道，调用方（curl 默认无超时，但监控脚本可能自设）需知悉。

## 11. 测试计划

**单元测试（cargo test）**

- `backoff_ms` 序列：base=1000 → [1000, 2000, 4000, 8000...]；base 边界 100/60000。
- drain（临时 SQLite 文件，渠道 type 用非法值 `"nope"` 使发送零出网即失败）：
  - 耗尽路径：入队 → drain → push_logs 终态 failed + retries 正确 + 队列清空；
  - 过期路径：伪造 `created_at` 超 1h → drain 判 `retry expired` 不发送；
  - 禁用任务跳过；乐观占位（rows_changed=0 跳过）。

**端到端（tests/e2e.sh）**

本地 webhook 接收器新增 flaky 路径（`/flaky?fail=N`：前 N 次 500，之后 200）：

| 场景 | 断言 |
|---|---|
| 同步重试成功 | max=3、base_ms=100、fail=2 → 响应 ok + `retries:2`，耗时 ≥ 300ms |
| 同步重试耗尽 | fail=999 → failed + `retries:3` |
| 异步入队 | mode=async、fail=1 → 首响 `retrying`；随后轮询 messages（兼触发 drain）出现 ok 行 + retries:1 |
| 边界校验 | max=11 / base_ms=50 → 创建任务 400 |
